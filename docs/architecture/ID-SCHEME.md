# Toothlogy Identifier Scheme

**Document ID:** `TL-DOC-IDSCHEME-001`
**Governed by:** Constitution P6 — *every important object has a stable public ID*

> **IDs are assigned once and never reused, even after deletion.**
>
> Reuse makes history ambiguous. An audit entry naming `TL-MOD-BOOKING-001`
> must refer to exactly one thing forever; if that ID were later reassigned, the
> audit trail would silently describe the wrong module — and an audit trail that
> can lie is worse than none.

---

## Two kinds of identifier

Toothlogy has two, and conflating them causes real confusion, so they are kept
visibly distinct.

| | Architecture IDs | Record IDs |
|---|---|---|
| Names | design objects — divisions, modules, permissions | database rows |
| Written by | a human, in the registry | code, at runtime |
| Example | `TL-CORE-HTTP-001` | `usr_01JF3QK8ZR7X2V9NBQ4C6T5MHD` |
| Lives in | `src/registry/`, documentation | the database, URLs |
| Defined in | this document | `src/platform/kernel/ids.ts` |

---

## 1. Architecture IDs

### Grammar A — modules and certifications

```
TL-<DOMAIN>-<OBJECT>-<NNN>
```

Used for **modules** and **certification IDs**, matching the founding
specification's own examples:

```
TL-DISCOVERY-DENTIST-001      module
TL-APPOINTMENT-BOOKING-001    module
TL-PATIENT-RECORD-001         module
TL-MARKETPLACE-PRODUCT-001    module
TL-FE-HOME-001                certification
TL-APT-BOOKING-001            certification
TL-USER-RECORDS-001           certification
```

### Grammar B — every other registry kind

```
TL-<KIND>-<NAME>-<NNN>
```

A kind token keeps the namespaces separate, so a page and an API cannot collide:

| Kind | Token | Example |
|---|---|---|
| Division | `DIV` | `TL-DIV-10-DISCOVERY` |
| Plugin | `PLG` | `TL-PLG-GST-INDIA-001` |
| Tool | `TOOL` | `TL-TOOL-SEARCH-001` |
| Page | `PAGE` | `TL-PAGE-HOME-001` |
| Component | `CMP` | `TL-CMP-BUTTON-001` |
| API | `API` | `TL-API-HEALTH-001` |
| Entity | `ENT` | `TL-ENT-USER-001` |
| Role | `ROLE` | `TL-ROLE-PATIENT-001` |
| Integration | `INT` | `TL-INT-EMAIL-001` |
| Event | `EVT` | `TL-EVT-USER-CREATED-001` |
| Notification | `NOTIF` | `TL-NOTIF-WELCOME-001` |
| Feature flag | `FLAG` | `TL-FLAG-DESIGNSYSTEM-REF-001` |
| Test suite | `TEST` | `TL-TEST-REGISTRY-001` |
| Document | `DOC` | `TL-DOC-CONSTITUTION-001` |

### Divisions are the exception

```
TL-DIV-<NN>-<SLUG>        TL-DIV-01-CORE … TL-DIV-35-DEVOPS
```

The number is the division's permanent identity. Divisions are never
renumbered, and a retired division's number is never reissued.

### Rules

1. Uppercase, hyphen-separated, ending in a three-digit counter (except
   divisions).
2. **Globally unique across every registry.** Enforced by
   `validateRegistry()`; a duplicate fails CI.
3. The counter distinguishes siblings — a second discovery module is
   `TL-DISCOVERY-DENTIST-002`, not a rename of `-001`.
4. **Renaming is allowed; renumbering is not.** A module's `name` may change
   freely; its `id` may not.
5. Retiring an object sets `status: 'deprecated'`. The entry stays, so the ID
   stays claimed.

## 2. Permission keys

Permissions use dotted keys rather than `TL-` IDs, because they are read
constantly in code and in policy discussions, where structure beats a counter:

```
tl.<division-slug>.<resource>.<action>[.<qualifier>]

tl.core.user.read.self
tl.core.organization.manage
tl.security.audit.read
```

Renaming a permission is a **breaking change**: it silently widens or narrows
access, and requires migrating every `RoleAssignment` that referenced it.

---

## 3. Event names

`SCREAMING_SNAKE_CASE`, **past tense**, because an event is a fact that already
happened — not a command:

```
APPOINTMENT_CONFIRMED     ✅ a fact
CONFIRM_APPOINTMENT       ❌ a command
```

Every name is registered in `src/registry/events.ts` before it can be published;
the bus rejects unregistered names, so a typo fails immediately instead of
silently reaching no subscriber.

## 4. Record IDs

Prefixed ULIDs, generated by `src/platform/kernel/ids.ts`:

```
usr_01JF3QK8ZR7X2V9NBQ4C6T5MHD
└┬┘ └──────────┬─────────────┘
 │             └── ULID: 48-bit timestamp + 80 bits of randomness
 └── entity prefix
```

**Why not an auto-increment integer:** sequential IDs in URLs are an
enumeration vulnerability. `/patients/1042` invites `/patients/1043`, and these
IDs appear in URLs.

**Why not a plain UUID v4:**

- The **prefix** makes an ID self-describing. `usr_…` in a log or a support
  ticket is instantly identifiable, and passing a clinic ID where a user ID was
  expected is caught by a cheap check rather than a confusing "not found".
- **Time ordering** keeps B-tree inserts local instead of scattering writes
  across the index — which matters once tables are large.
- **Crockford base32** omits I, L, O and U, so an ID read aloud to support or
  typed off a screen survives the round trip.

Prefixes are registered centrally in `ID_PREFIXES` so two divisions cannot
choose the same one — a collision would defeat the purpose of having a prefix.

## 5. Reserved IDs

These are claimed permanently, with no implementation behind them
(Constitution P6):

| ID | Reserved for | Phase |
|---|---|---|
| `TL-DISCOVERY-DENTIST-001` | Dentist discovery | 4 |
| `TL-APPOINTMENT-BOOKING-001` | Appointment booking | 4 |
| `TL-PATIENT-RECORD-001` | Patient dental record | 6 |
| `TL-MARKETPLACE-PRODUCT-001` | Marketplace product catalogue | 9 |

## 6. Adding an ID

1. Check it is unused — `validateRegistry()` will reject a duplicate anyway.
2. Add the entry to the right registry file with an **honest status**
   (`planned` if nothing exists yet).
3. Run `npm run registry:validate`.
4. Reference the ID from the code it names, so the link is discoverable in both
   directions.
